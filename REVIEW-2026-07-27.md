# Codebase Review: Mythcast
**Date:** 2026-07-27
**Stack:** Next.js 16 + Convex + Clerk + Neo4j Aura, @react-pdf/renderer, Tailwind v4
**Project type:** Web app (mythology/culture generator), v1.0.0, all 11 spec build-phases marked complete

## Executive Summary

The generation engine (culture → pantheon → myths → drift simulation) is genuinely strong — traceable, well-commented, and the code visibly implements the spec's design principles (flagged mismatches, event-biased drift, decay-only omission) rather than paraphrasing them. Visually, the theming system, typography, and codex/lineage/graph views are polished and read as a coherent product. The gap is almost entirely in **user-facing steerability and connective tissue**: every seed parameter is hardcoded, the two routes (`/` and `/world`) don't link to each other, a fully-built manual-event-injection feature has no UI, and the one PDF export deliverable has a real rendering bug. None of this requires re-architecture — it's wiring and finishing work on top of a solid generation core.

## High Priority Findings

### 1. Codex PDF export: title overlaps subtitle text
**What:** In both "styled" and "printer-friendly" PDF exports, the culture-name title and the italic summary paragraph directly below it visually overlap and are unreadable at the intersection. Confirmed on both modes — same root cause in the shared template.
**Why it matters:** The codex PDF is one of the two first-class deliverables in the spec (Section 8: "the story experience"). This is the artifact people would actually print or share, and right now the header is broken on every export.
**Suggested action:** `src/lib/codex/CodexDocument.tsx:38-43` — the `title` style is `fontSize: 26` with only `marginBottom: 4` and no explicit `lineHeight`, so it inherits the page's `lineHeight: 1.5` and collides with the `summary` block. Give `title` its own `lineHeight` (e.g. `1.1`) and bump `marginBottom` to something proportional to a 26pt heading (10-14).
**Effort estimate:** Quick fix.

### 2. Seed parameters are 100% hardcoded — the "steerable" design principle has no UI
**What:** Both `src/app/page.tsx` (`demoSeed`) and `src/app/world/page.tsx` (`DEMO_SEED`) use fixed, inline `CultureSeedParams`. There is no form, picker, or any UI element letting a user choose climate, threat model, kinship structure, etc.
**Why it matters:** Spec Section 2 states steerability is "core, not a stretch feature," and Section 3 lists 8 seed parameters as the entire input surface of the app. Right now Mythcast is a fixed demo, not a generator a user can actually drive — this is the single largest gap between the spec's stated ambition and what's shippable today.
**Suggested action:** Build a seed-params form (8 selects/radios) gating "Generate demo world," replacing the hardcoded `DEMO_SEED` in `world/page.tsx`.
**Effort estimate:** Half-day (the generator/pipeline side already accepts arbitrary `CultureSeedParams` — this is UI-only work).

### 3. Manual event injection is fully built on the backend, unreachable from the UI
**What:** `convex/simulation.ts` exports `injectEvent` — a complete, well-documented mutation ("queues a manual event for a not-yet-reached generation... wins over any procedural roll") — but no component calls `api.simulation.injectEvent` anywhere in `src/`.
**Why it matters:** Spec Section 7 names manual injection as one of two co-equal event sources ("you steer live, dropping in 'a great war happens now'"), and Section 2's steerability principle again applies. Today `world/page.tsx` only ever calls `runToCompletion`, so every run is 100% procedural — the feature that would make the drift simulation feel authored rather than random is invisible to users despite being done.
**Suggested action:** Add a lightweight UI (e.g. a "queue an event" control before/during `runToCompletion`, or switch to stepping one generation at a time via `advanceGeneration` with an inject-event affordance between steps).
**Effort estimate:** Half-day.

### 4. No navigation between `/` and `/world` — two disconnected experiences
**What:** There is no header, nav bar, or single `<Link>` anywhere in `src/app` or `src/components` connecting the routes. `/` renders a client-only stub pipeline (`runPipeline`, no Convex) with its own demo seed; `/world` is the real Convex-backed flow with a different demo seed. A user landing on `/` has no way to discover `/world` exists, and vice versa.
**Why it matters:** `/` is effectively a dead end showing a different (and less capable) demo than the actual product. This is the first thing any visitor sees.
**Suggested action:** Either add a minimal nav/link from `/` to `/world`, or retire `/`'s stub pipeline demo now that `/world`'s real pipeline exists and make `/` the entry point for the real flow instead.
**Effort estimate:** Quick fix (add nav) to Half-day (consolidate the two demos).

## Medium Priority Findings

### 5. Demo run is deterministically seeded — first impression undersells the drift engine
**What:** `world/page.tsx` always calls `createCulture`/`startRun` with `rngSeed: 1` / `seed: 1`. Running the demo (repeatedly, in this review) always produces the exact same result: one war-triggered mutation at generation 4, and **zero** passive decay across the other 7 "quiet" generations, even though `mutation.ts` implements a 12%-per-generation decay chance specifically so quiet runs still show some drift (spec Section 5: "a 'quiet' simulation run... still shows some drift over many generations").
**Why it matters:** This isn't a bug in the mechanism — 7 independent 12% rolls landing on zero hits is plausible (~42% chance) — but because the seed is hardcoded, *every single visitor* gets this same undersell of the core "myths drift coherently over time" pitch, deterministically, forever.
**Suggested action:** Vary the demo seed per run (e.g. seed off `Date.now()` once seed params are user-facing per Finding #2), or bump `DECAY_CHANCE` slightly for a more legible demo.
**Effort estimate:** Quick fix.

### 6. Auth is wired but never surfaced — no sign-in prompt, no per-user culture list
**What:** Clerk + `ConvexProviderWithClerk` are fully configured, and `convex/cultures.ts` derives `owner` from `ctx.auth.getUserIdentity()` — but falls back to `"unauthenticated-dev"` when there's no identity, and no UI component ever renders `<SignedIn>`/`<SignedOut>`/`<UserButton>` or links to `/sign-in`. There's also no "my cultures" list — `cultureId` lives only in local `useState`, so refreshing `/world` loses everything and there's no way to revisit a past generation.
**Why it matters:** The schema already models per-owner separation (`cultures.by_owner` index) but it's unreachable — every anonymous visitor's generations are attributed to the same fallback owner, and nobody can come back to what they made.
**Suggested action:** Decide (with Nae) whether auth-gating is in scope for this phase; if so, add a sign-in prompt + a `cultures.listByOwner` query and a simple history list. The soft-fallback comment in `cultures.ts` frames this as a deliberate Phase-10 stub, but Phase 10 is marked done — worth confirming this is known debt rather than a missed step.
**Effort estimate:** Half-day to Multi-day depending on scope.

### 7. Multi-step generation flow has no intermediate progress feedback
**What:** `generateWorld()` in `world/page.tsx` chains 7 sequential Convex calls (create culture → create pantheon → create myths → sync 2 graph writes → start run → run to completion). The only user-visible state is the button flipping to "Generating world…" for the whole duration (~10-13s observed).
**Why it matters:** A single opaque loading state for a multi-stage pipeline reads as "stuck" past a few seconds, especially for ND users who benefit from visible progress on longer waits (per this project's ND-first design goal).
**Suggested action:** Surface which step is running ("Building culture… → Generating pantheon… → Simulating drift…") — even simple text-swap per await is enough; a progress bar isn't necessary.
**Effort estimate:** Quick fix.

### 8. Sign-in/sign-up pages use unstyled default Clerk UI
**What:** `/sign-in` and `/sign-up` render bare `<SignIn />`/`<SignUp />` with no `appearance` theming. Every other surface in the app uses the Fraunces display font and the 5-theme `--mc-*` color system; the auth pages are plain white Clerk-default cards with system fonts.
**Why it matters:** Jarring visual break if/when these pages are actually reached (see Finding #6 — currently they aren't reachable from any nav, compounding this).
**Suggested action:** Pass an `appearance` prop to `<SignIn>`/`<SignUp>` matching the shell's ink/parchment palette, once auth is actually surfaced.
**Effort estimate:** Quick fix.

### 9. Unhandled promise rejections in two `useEffect` data loads
**What:** In `world/page.tsx`, `getRelationshipGraph({ cultureId }).then(setRelationshipGraph)` and `getLineageView({ foundingMythId }).then(...)` have no `.catch`. If either Convex action throws (e.g. Neo4j hiccup), the promise rejects silently and that section just stays empty with no error message — unlike `generateWorld()`, which does catch and surface errors via `setError`.
**Why it matters:** Inconsistent error handling — one code path in the same file tells the user something went wrong, two others fail silently.
**Suggested action:** Add `.catch` handlers that set a local error string, mirroring the pattern already used in `generateWorld()`.
**Effort estimate:** Quick fix.

## Low Priority / Nice-to-Have

### 10. Name generator produces bare 2-letter names about half the time for "flowing"-texture cultures
**What:** `src/lib/names.ts:35` rolls `segments = rng.int(1, 2)` — a 50/50 coin flip on syllable count, independent of texture. For the "flowing" naming texture (`CV`/`CVV` shapes, no coda), a single-segment roll produces bare 2-character names. Observed directly in this review's demo pantheon: **Mi, Ni, Wu, No** (4 of 5 gods), vs. the one 2-segment name, **Naenae**.
**Why it matters:** Spec's stated goal is names/cultures that "feel lived-in rather than assembled" — a pantheon where 80% of gods have 2-letter names reads as thin, not evocative.
**Suggested action:** Bias segment count by texture (e.g. `flowing` and `clipped` textures, which have short/no-coda shapes, weight toward 2 segments more often), or set a minimum character-length floor independent of segment count.
**Effort estimate:** Quick fix.

### 11. Zero `aria-*` attributes anywhere in the UI
**What:** No `aria-*` usage across `src/app`/`src/components`. Specific spots that would benefit: the `ThemePicker` theme/light-dark pill rows behave like radio groups (single active selection) but expose no `role="radiogroup"`/`aria-pressed`; the `LineageViewer`'s generation `<select>` (`world/page.tsx:138`) has no associated `<label>`.
**Why it matters:** Minor for a solo/small-audience MVP, but cheap to fix now before more interactive surfaces are added.
**Suggested action:** Add `aria-pressed` to the theme/variant pill buttons, wrap the myth-select in a `<label>`.
**Effort estimate:** Quick fix.

### 12. Themed panel vs. shell-chrome contrast is a deliberate choice worth double-checking visually
**What:** `globals.css` documents (in a comment) that the outer page shell intentionally stays a fixed light/dark parchment-ink pair regardless of the selected culture theme, so the themed panel reads as "pages inside a book cover." In practice, picking a *dark* culture theme leaves a light parchment frame around a dark card — visually a bit more jarring in person than the comment's framing suggests, especially since `DARK`/`LIGHT` toggle language reads like a page-wide mode switch rather than a panel-only one.
**Why it matters:** Not a bug — it's designed and explained — but worth a quick look together since the toggle's naming may set the wrong expectation.
**Suggested action:** No action needed unless it reads wrong in person; if so, consider renaming the toggle labels (e.g. "panel: light/dark") to set expectations, rather than changing the mechanism.
**Effort estimate:** N/A (design confirmation, not a fix).

### 13. Several Convex functions have no frontend caller
**What:** `gods.listByCulture`, `myths.get`, `myths.listByCulture`, `mythVariants.insertVariant`, `mythVariants.createAndSync`, `mythVariants.listByCulture`, `simulation.getRun`, `simulation.listEvents`, `simulation.listLineageHeads` are exported but never called from `src/`.
**Why it matters:** Some of these (`insertVariant`, `createAndSync`) are plausibly internal helpers called by other Convex functions rather than the frontend, which is fine. `simulation.listEvents` in particular would be genuinely useful paired with Finding #3 — an event log showing what fired each generation — and `myths.get`/`listByCulture` are the kind of read path a "my cultures" history view (Finding #6) would need.
**Suggested action:** No action beyond keeping in mind while addressing Findings #3 and #6 — these read paths are the ones you'd wire up first.
**Effort estimate:** N/A (tracked for context, not standalone work).

## Dimension Summaries

### UI/UX: 🟡 Polished where it's finished, but two entry points and a broken PDF header
Theming, typography, and card/graph layouts are genuinely well-designed. The gaps are structural (no nav, no progress feedback) and one concrete rendering bug (Finding #1), not aesthetic weaknesses.

### Features: 🟡 Strong generation core, thin steering surface
Culture → pantheon → myth → drift is real and works end-to-end, including the codex/lineage/relationship-graph outputs. What's missing is entirely on the "let the user drive it" side: seed params, manual event injection, and any persistence/history of past generations.

### MCP: — Not applicable
Mythcast doesn't currently expose or consume MCP tools, and nothing about its data (per-user generated worlds) obviously calls for it beyond what Convex/Clerk already provide. Not flagged as a gap.

### Architecture: 🟢 Clean
No `any` casts outside generated code, no TODO/FIXME markers, consistent file organization matching the spec's own layer boundaries (culture/pantheon/myth/simulation/validator), and code comments throughout explicitly trace back to spec sections — genuinely unusual discipline for an MVP.

### Infrastructure: 🟢 Solid for this stage
Env vars, Convex + Clerk + Neo4j all correctly wired and live-tested in this review. No infra findings worth flagging at this stage.

### DX: 🟢 Good
12 test files covering the generation/validation/mutation logic (the highest-value area to test), README and spec doc both accurate and current, no stale comments found.

## Strengths

- **Traceability is real, not aspirational.** Every generated field visibly cites its upstream cause in code comments and, in myths, in `derivedFrom` — the spec's traceability requirement (Section 3/6) shows up as an actual invariant, not just a design doc line.
- **Flag-based exceptions are implemented as designed.** Personality mismatches, tension, and drift diffs all surface as explicit UI affordances (marginalia styling, diff strikethrough) rather than being silently absorbed — exactly the spec's "flag, don't hide" philosophy in Section 6.
- **The lineage diff view is a genuine highlight.** Showing struck-through old text → new text per generation (Finding-adjacent, seen at Gen 4 in this review) is a clean, legible way to make "watching drift happen" visible, which is the spec's stated payoff for this feature.
- **Code comments consistently explain *why*, tied to spec sections**, which made this review meaningfully faster and will do the same for future contributors.
